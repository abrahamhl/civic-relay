# Plan de ejecución · PCI y biblioteca científica abierta

**Fecha:** 07-11-2026  
**Objetivo:** convertir la capa de precisión de SENDA en un artefacto de software
real, abierto y verificable que no exista ya empaquetado: **PCI v0.1 —
Proof-Carrying Inference**, un sobre de evidencia para afirmaciones numéricas
offline, con implementación de referencia, papers y biblioteca pública.

## 0. Norte

Que cualquier número mostrado por un sistema de emergencia pueda ser comprobado
sin red, por un tercero, con el código y los datos del propio sistema:

1. qué fórmula lo produjo;
2. con qué entradas y tolerancias;
3. con qué clase de procedencia (ejercicio, campo, validado, derivado);
4. con qué regla de redondeo o cota se mostró;
5. y con un hash que detecte cualquier deriva.

No prometemos una prueba criptográfica de que el cálculo se ejecutó. PCI es un
**sobre de evidencia comprobable**, no un SNARK. Esa distinción está en la
especificación y en cada paper.

## 1. Lo que ya existe y lo que falta

Ya existe en producción:

- `precision-lab.mjs`: Beta-Binomial, erasure exacto, DTN, RSSI/CRLB, SEIR RK45,
  ledger y sello de priors.
- Base de priors sellada y sección `#precision-lab` en tres idiomas.
- 123 pruebas y verificación real en navegador.

No existe todavía:

- un estándar de sobre de evidencia con verificador independiente;
- un paquete open source instalable y versionado;
- papers públicos con matemáticas, tablas y paquetes de reproducción;
- una biblioteca `/research` en la web;
- un runbook de publicación externa (GitHub, npm, arXiv, Zenodo).

## 2. El artefacto: PCI v0.1

**Nombre:** SENDA PCI — Proof-Carrying Inference.  
**Formato:** JSON canónico + SHA-256 + firma ECDSA P-256 opcional.  
**Promesa:** un verificador de ~300 líneas puede aceptar o rechazar una
afirmación numérica sin confiar en quien la produjo.

### Clases de procedencia

| Clase | Significado | Requisito |
|---|---|---|
| `EXERCISE` | Rango declarado de ejercicio; no medición | Nota y límites explícitos |
| `SIMULATED` | Resultado de un modelo o simulación | Método, tolerancias y límites |
| `FIELD` | Observación de campo trazable | Fuente y digest de la fuente |
| `VALIDATED` | Contrastado contra una referencia independiente | Fuente, digest y protocolo |
| `DERIVED` | Calculado a partir de claims anteriores | Lista de claims padres y digest |

### Niveles de verificación

- **L0 estructural:** esquema, tipos, campos obligatorios.
- **L1 integridad:** hashes de entradas, resultado y payload.
- **L2 visualización:** el texto mostrado cumple la regla declarada o la cota.
- **L3 procedencia:** la clase y la fuente son coherentes.
- **L4 firma:** firma ECDSA P-256 verificada con una clave pública declarada.

### No-claims

- No demuestra que el runtime no esté comprometido.
- No sustituye una auditoría independiente del modelo.
- No convierte un prior de ejercicio en evidencia de campo.
- No es una prueba de conocimiento cero ni una prueba de ejecución verificable.

## 3. Ciclos cerrados

### Ciclo 1 · Estándar y referencia open source

**Entra:** fórmulas actuales, decisiones de sello y el caso de hidratación.  
**Sale:** `packages/senda-pci` con `SPEC.md`, `src/index.mjs`, tipos, 15+ pruebas,
ejemplo reproducible y LICENSE MIT.  
**Criterio de salida:** `node --test` en verde; el verificador detecta mutaciones
de entradas, resultado, display, procedencia y firma.  
**Verificación:** `cd packages/senda-pci && node --test "test/*.test.mjs"`.

### Ciclo 2 · Papers y paquete de reproducción

**Entra:** especificación, fórmulas y datos de la sección de precisión.  
**Sale:** tres technical reports:

1. **SENDA-TR-2026-01** — *Proof-Carrying Inference for Offline Emergency
   Software*: modelo, canonicalización, verificación, seguridad y caso de estudio.
2. **SENDA-TR-2026-02** — *Exact Erasure Tails and Delay Bounds for
   Store-Carry-Forward Emergency Messaging*: derivaciones, tablas y límites.
3. **SENDA-TR-2026-03** — *Display Determinism Across JavaScript Runtimes for
   Adaptive ODE Solvers*: el caso SEIR Node/Chromium, regla de visualización y
   protocolo experimental.

Cada paper incluye abstract, matemáticas, tablas, límites, referencias, BibTeX,
HTML, PDF y hash SHA-256.  
**Criterio de salida:** PDF generado, HTML navegable, hashes en el manifest y
números de tabla reproducibles con el paquete.  
**Verificación:** `npm run research:build && npm run research:pdf`, y
`node --test "tests/*.test.mjs"`.

### Ciclo 3 · Publicación en la web

**Entra:** papers, manifest y paquete.  
**Sale:** `/research`, `/es/research/`, `/nl/research/` con abstracts traducidos,
descargas PDF/HTML/BibTeX/ZIP, sello de integridad y comandos de reproducción.  
**Criterio de salida:** build estático, tres locales, enlaces desde la portada y
desde la superficie Science; Playwright sin errores; deploy a producción.  
**Verificación:** smoke de producción a 390/1440 px y descarga de cada artefacto.

### Ciclo 4 · Validación adversarial entre runtimes

**Entra:** PCI v0.1 y los papers.  
**Sale:** banco de pruebas que ejecuta los mismos claims en Node, Chromium y un
verificador independiente en Python; matriz de valores crudos, pasos y displays;
informe de divergencias.  
**Criterio de salida:** ningún claim publicado cambia de display entre runtimes;
toda divergencia cruda está cubierta por una cota declarada.  
**Verificación:** `node scripts/research/cross-runtime.mjs` y comparación de
hashes de display.

### Ciclo 5 · SDK y CLI para terceros

**Entra:** paquete de referencia.  
**Sale:** `npx @senda/pci verify claim.json`, `@senda/pci` como dependencia,
ejemplos de integración con la app de campo y un verificador mínimo en otro
lenguaje.  
**Criterio de salida:** un tercero puede verificar un claim sin leer el código de
SENDA; el CLI devuelve códigos de salida estables.  
**Verificación:** tests del CLI y verificación cruzada JS/Python.

### Ciclo 6 · Adopción y gobernanza

**Entra:** estándar, papers y SDK.  
**Sale:** RFC público, política de seguridad, versionado semántico, changelog,
plantilla de claim, guía de contribución y lista de implementaciones.  
**Criterio de salida:** proceso para cambiar el estándar sin romper claims
antiguos; dos implementaciones independientes.  
**Verificación:** revisión de compatibilidad y pruebas de claims v0.1 con
verificador v0.2.

### Ciclo 7 · Evidencia de campo

**Entra:** claims `EXERCISE` y `SIMULATED`.  
**Sale:** protocolo de ensayo, plantilla de claim `FIELD`, cadena de custodia,
digests de fuentes y actualización de priors con evidencia real.  
**Criterio de salida:** ninguna afirmación operativa sin claim `FIELD` o
`VALIDATED`; los priors de ejercicio se sustituyen, no se maquillan.  
**Verificación:** auditoría de procedencia y reproducción de una muestra.

## 4. Perspectivas de trabajo

| Perspectiva | Pregunta | Entregable |
|---|---|---|
| Matemática | ¿La fórmula es exacta, acotada o aproximada? | Derivaciones y cotas |
| Software | ¿Puede un tercero verificarlo? | Paquete, CLI, tests |
| Ciencia | ¿Es reproducible y falsable? | Papers, tablas, protocolo |
| Open source | ¿Puede adoptarse sin permiso? | MIT, SPEC, RFC, ejemplos |
| Producto | ¿Resuelve un dolor real? | SDK y caso de uso offline |
| Institucional | ¿Sirve para una compra o un piloto? | Evidencia y límites |
| Seguridad | ¿Qué falla si hay adversario? | Modelo de amenaza y firma |
| Ética | ¿Qué no debemos afirmar? | No-claims y clases |
| Operación | ¿Cómo se despliega y se mantiene? | CI, versiones, hashes |
| Comunicación | ¿Se entiende en 30 segundos? | Biblioteca y abstracts |

## 5. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Sobreafirmar novedad | Sección de prior art y no-claims en SPEC y papers |
| Confundir hash con prueba | Niveles L0–L4 y lenguaje explícito |
| Papers sin revisión | Etiqueta `TECHNICAL REPORT · NOT PEER REVIEWED` |
| Deriva de artefactos | Manifest con SHA-256 y verificación en la página |
| Dependencia de un runtime | Regla de display con cotas y banco cross-runtime |
| Paquete sin mantenimiento | Versión 0.1.0, RFC y política de compatibilidad |
| Publicación externa bloqueada | Runbook de una orden para GitHub/npm/Zenodo/arXiv |

## 6. Métricas

- 100 % de claims publicados con hash y clase de procedencia.
- 0 discrepancias de display entre Node y Chromium en la matriz publicada.
- 100 % de PDFs con hash verificado en el manifest.
- Verificador independiente que acepta los claims válidos y rechaza los mutados.
- Tiempo de verificación de un claim < 50 ms en un portátil.
- Número de claims `FIELD`/`VALIDATED`: hoy 0; objetivo del Ciclo 7.
